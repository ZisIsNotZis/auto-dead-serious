# Catalogue assessment
Authored method document derived from ../product/catalogue.md; anchors are agent-designed implementation of the approved assessment scope, not user-supplied measurements.
## Scales
The existing 0–4 creativity/current-usefulness calibration is disputed; ../product/catalogue-calibration.md owns the owner's corrections and provisional replacement. These anchors document how the draft records were assessed, not a newly approved ranking standard; do not add decimal places or silently rescore the collection.
Scores are ordinal judgements, not measured intervals; use integers 0–4 or unknown, independently per aspect, with a reason, evidence confidence and inspection level. Missing evidence is unknown, never zero. Four requires unusually strong supporting evidence, not excitement or volume.
| Aspect | 0 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|---|
| Creativity | Inspected contribution is an unmodified repeat with no interesting angle | Familiar approach with a minor personal variation | Interesting, explainable adaptation or combination | Distinctive thesis or synthesis worth exploring beyond its author | Exceptionally distinctive and interesting contribution supported by strong comparison evidence |
| Current usefulness | Inspected artifact cannot deliver any named worthwhile current outcome | Narrow learning/reference value or heavily manual fragment | Concrete bounded use plausible from implemented behavior, with material limits | Coherent useful workflow supported by inspectable output or recorded end-to-end evidence | Compelling real use with independently corroborated outcomes for its audience |
| Expected usefulness | Even its stated finished scope has no identifiable worthwhile outcome | Small convenience or narrow learning outcome | Meaningful bounded benefit to a named user | Important capability or substantial workflow improvement if the stated scope succeeds | Potentially game-changing benefit with a credible mechanism and strong evidence of the problem's importance |
| Impl progress | Confirmed idea/specification only, with no implementation of its core behavior | Core fragments exist but do not form an end-to-end slice | A core scenario is implemented; important intended behavior remains absent | Intended core slice is integrated with relevant tests/output evidence; material acceptance limits remain | Stated intended scope meets its acceptance with revision-bound executed evidence, not source presence alone |
| Presentability | Inspected surface is misleading or gives no usable orientation | Purpose discernible only through source or incomplete instructions | Purpose, limitations and an actionable entry point are documented | Clear front door, concrete example/demo/output, prerequisites and honest limits | Fresh-user path and delivered artifact are independently verified and compelling |
Creativity reasons separately mention interestingness and the scope of novelty evidence; a category comparator is not proof of duplication. Creativity may be assessed provisionally from local evidence while global novelty stays unknown.
Current usefulness may receive a source-supported provisional score, but no runtime success is claimed without actual execution evidence; cite producer and revision of prior run records.
Expected usefulness must state the bounded finished scope, target user and advantage; if finished scope cannot be established, use unknown rather than inventing a roadmap. Separately describe delivery likelihood as evidenced, uncertain or blocked, with reason; do not multiply it into expected usefulness.
Impl progress is relative to stated scope, so a complete small utility may outrank an incomplete ambitious platform. Presentability is independent of internal implementation merit.
## Evidence and record
One assessment per submodule path declared in ../../.gitmodules; capture parent gitlink, child HEAD, bounded dirty-state limits, evidence paths/headings or lines, and observation time. Unavailable checkouts remain explicit unknown records; never fetch or initialize them under this mandate. A leading minus in git submodule status alone is a registration signal, not proof files are unavailable: confirm the child Git root, HEAD and required files before deciding availability.
Each record contains description, stated scope/audience, five ratings with short reasons, confidence (low/medium/high) and inspected-versus-executed status, three membership-route judgements (supported/unsupported/unknown), distinctive contribution, relevant public alternatives or comparison question, editorial verdict/reason and next decisive step.
Confidence concerns support for the claim, not project quality; source inspection may strongly support existence of an implementation but only weakly support runtime compatibility. Prior pilot scores are input evidence, not automatically current assessments under these corrected anchors.
Inspect the README and declared docs first, then the smallest representative implementation/test/result set needed to decide; do not read dependency trees, secrets, personal payloads, model weights or live logs. Report an evidence limit rather than inventing a score or expanding indefinitely.
Private or personal-content projects receive sanitized assessment summaries; no personal content, credentials, private snippets or hidden project details go into public searches or committed reports. If safe assessment cannot be separated from private data, mark privacy-limited unknown rather than publishing it.
## Membership and prominence
A supported OR route supports retain even when other routes are weak; usefulness requires meaningful differentiation, creativity need not be utilitarian, and substantial work can include an honest negative research result.
Use remove candidate only when all three routes are unsupported with positive inspection evidence sufficient to explain why nothing worthy was found; unknown evidence produces undecided, not removal. This is a recommendation, never cleanup authority.
For retained projects, use showcase candidate when an inspectable user-facing slice merits fresh verification; incubate when the thesis or work merits keeping but isn't ready; repair when a concrete in-scope presentation/evidence defect hides or misrepresents existing merit. Showcase candidate is a verification queue, not permission to feature an unverified artifact, so missing fresh execution alone does not disqualify it. A supported route always means retain, even under private scope; uncertainty about other routes does not turn it into undecided. Give the reason rather than deriving these labels from a numeric average.
## Public comparison
Use current primary public sources for consequential overlap claims and retain URLs, retrieval context, relevant excerpts and limits. Compare user tasks and mechanisms, not just names or feature lists; do not claim performance, superiority, historical priority, legal status or copying from README similarity.
Parent owns public research because the selected scout role lacks web tools. Existing bounded comparison is at ../result/catalogue-comparison.md; new local investigators supply generic comparison questions, and unsettled differentiation remains unknown until parent follow-up.
## Storage and projection
Authored per-project facts live in ../result/catalogue/<submodule-path>.json; ../result/catalogue/README.md is their generated browsing view, not a separately editable ratings table. The parent root README is outside this assessment's edit scope.
Run python3 scripts/catalogue.py --render from the parent root to validate and regenerate the browsing view, --check to verify it, and --self-test to exercise safe failure fixtures. The script uses Python's standard library and read-only Git, with no project-code execution or external dependencies.
The --import-handoffs DIRECTORY command adopts a complete set of investigator drafts once and refuses existing source files; shape normalization is mechanical, while parent calibration edits the authored records in place. Runtime-managed handoffs are not a second permanent source.
## Completion checks
Check the assessment set against the .gitmodules path set: each path exactly once, no extras, all required fields and valid rating/verdict values, and cited local evidence resolves. Validate structure mechanically; parent synthesis judges evidence and cross-project anchor consistency, not a formula.
No fresh independent review is required in discussion mode; results remain source-inspected investigator judgements with explicit unverified runtime/visual/novelty limits, not independent acceptance or an asserted absence of defects.
