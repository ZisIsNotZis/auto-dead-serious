## backseat

- [pitfall] `.scratch/tickets/wp-insight-session.md:15,26-37` - after a 125-hour stop/start the persona context carried "[洞察候选] 这一轮已经连续活跃 124.5 小时": `InsightMiner` read a persisted `state.session_start_wall` and only reset it when the last observation was already older than the gap, so once observations resumed the stale value counted the whole downtime as continuous activity, and a wrong candidate was re-injected into the frozen context every round - policy candidate (a persisted derived value must be recomputed from the ground-truth timeline, or a restart resurrects it as a false fact).
- [pitfall] `.scratch/tickets/wp-shown-receipt.md:6-7` with `.scratch/tickets/WP-RUNTIME-VERIFY.md:17` - all 366 `expressions` rows read `status=shown` because the engine's stdout was `DEVNULL`, so nothing was ever confirmed rendered; the ticket's own goal is "只有引擎确认落位才 shown, 无回执/超时都不得谎报 shown" - policy candidate (a success status is owned by the consumer's acknowledgement, never by the writer's own write).
- [pitfall] `.scratch/tickets/WP-FIX-P2.md:22-26` - frame files were named at second resolution (`%H%M%S`), so a big event and its sample in the same tick shared one `ref`; row-level eviction then deleted a file an exempt row still pointed at and left another row dangling - policy candidate (an identifier with too little resolution silently aliases distinct records; fix the key, not the symptom).
- [pitfall] `.scratch/tickets/wp-storage-evict.md:41` and `.scratch/tickets/WP-FIX-P2.md:79` - `freed_bytes` and `used_before - used_after` diverge whenever several rows share one path; the authoritative water level is the recomputed `used_after` and that had to be written into a docstring and a residual note - policy candidate (when two counters describe one quantity, name which one is authoritative).
- [pitfall] `.scratch/tickets/wp-shown-receipt.md:16,20` - `ReceiptReader` stored every reply in a dict and nothing removed the ids a `wait()` had already abandoned, so the dict grew once per timeout (the engine's ~0.5s cold start made the first one certain); fixed by recording `_abandoned_upto` - project-specific.

- [doc method] `docs/SCHEMA.md:26-30` against the code (`.scratch/tickets/WP-FIX-P2.md:28-31`) - the documented `status` closed set omitted `failed`, which the outlet already wrote; the fix was to add it to the prose - policy candidate (a closed set copied into prose rots against the code; the policy's `references_resolve` covers broken links, not a drifted enum).

## Top 5 by value

1. **A success status must be owned by the consumer's acknowledgement** (backseat `wp-shown-receipt.md:6-7`, 366/366 rows falsely `shown`) - the general policy has `unverified_is_not_pass` for acceptance, but nothing that forbids a pipeline from recording "done" on the strength of its own write.
2. **A derived value persisted across restarts resurrects as a false fact** (backseat `wp-insight-session.md:26-37`, "连续活跃 124.5 小时" poisoning the frozen context every round) - recompute from the ground-truth timeline so a restart self-heals; this is the concrete mechanism behind the policy's `fix_the_root` and `resumable`.
3. **A pipeline stage must report what it contributed** (litellmgen `01-flat-facts-merge.md:15-16,39`, one source contributed 0 of 3917 rows for an unknown period and looked healthy) - an empty source and a working source are indistinguishable unless the count is printed, and a rotting extraction rule must print its yield on every run.
4. **Two compared numbers must share a metric and a producer, and a limit that can silently change behaviour must not be derived** (causalmlp `report.md:139-146` exp(-loss) vs classification accuracy; litellmgen `04-vendor-doc-source.md:127-131` refusing to fill `max_tokens` from prose) - this generalises `citation_not_value` from documents to comparisons and defaults.
5. **The restart/verification must be proven by the loaded artefact, not by whatever answers** (litellmgen `01-flat-facts-merge.md:81-87`, two "successful restarts" served the old config; backseat `WP-INTEGRATION.md:10-11`, lane branches disappeared and only the recorded SHAs survived) - a status check is not a revision check, and the durable handle is the commit SHA written into the ticket.
