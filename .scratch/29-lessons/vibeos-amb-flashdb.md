# Lessons from vibeos, auto_maintain_bench, flashdb

Slug: `vibeos-amb-flashdb`. Read-only sweep; every finding names a file and a heading or line.
Judgements are `policy candidate`, `already covered by <rule>`, or `project-specific`. Anything I
concluded rather than read is marked **inference**.

## vibeos

Small project (three docs, 131 lines of markdown, no `.scratch`, no work record). Little incident
history; the findings are doc-hygiene ones rather than paid-for pitfalls.

- [doc method] `docs/vibeos-design.md:3` - "Status: implementation in progress" - while `docs/project-status.md` says "Closed as a milestone (2026-09-29)" and `README.md` says "closed (milestone)" - the same status fact lives in three files and two of them disagree - policy candidate (one home per fact; a stale status line is a lie the reader cannot detect).
- [doc method] `docs/vibeos-design.md#Verification` - "The README is the tested entry point and package manifests are the version source" - the project wrote down which file owns the commands and which owns the version number - policy candidate (project rule of the "one home per fact" kind, and it is the fix for the finding above).
- [project rule] `AGENTS.md` (vibeos, "core boundary") - "Never add app-name checks, command-name checks, application-specific UI, or application-specific behavior to core" and "A feature belongs in core only when it cannot be implemented as replaceable generated content" - a kernel-vs-content boundary stated as a prohibition, with generated content as the extension seam - policy candidate (the general form: never put an instance's name into the generic mechanism).
- [project rule] `AGENTS.md` (vibeos) - the four-step implementation order: "Model the smallest explicit state and mutation contract first", then "Make the UI render from that state and emit declared intents", "Keep deterministic local interactions local; use AI only for open-ended work", "Validate the relevant state transition... with tests" - project-specific as written, but the third clause is a real scoping rule an agent would get wrong unaided (an agent reaches for generation where a deterministic primitive suffices).
- [doc method] `docs/generation-harness-plan.md#Hardening backlog` - "They are not current security guarantees" and `docs/vibeos-design.md#Non-goals and risks` - the deferred work is named and disclaimed instead of being listed as present - already covered by `label_confidence` (a plan is not a result), and worth keeping as the reference pattern.
- [doc method] `.claude` is a symlink to `.agents` (`ls -la`), so the two agent-config trees are one tree - a one-home arrangement rather than duplicated skill sets - project-specific, but it is the cheap fix for the duplicated-config trap.

## flashdb

The richest of the three by far: a 78-ticket work record with explicit methodological corrections,
retractions, and instrument-validation boundaries. Almost everything here is a paid-for lesson
already written down somewhere in the project.

- [pitfall] `.scratch/STATUS.md:68` and `.scratch/active-work.md:9` - "commit `744caaa` marks the boundary before which every per-rung number was unusable" - four instrument defects (a median of per-window deltas so `achieved` exceeded `offered`; the `invalid`/`lag_p99_us`/`window_us`/`ceiling_us` fields never reaching `--metrics-json` "so the pre-registration's 'no rejected window' criterion was vacuous"; an unflushed trailing partial window leaving 448 completions unattributed; a ceiling applied to a group-aggregated quantity) - the measurement instrument, not the engine, invalidated an entire published result set - policy candidate (validate the instrument before its numbers are used or published, and bind every number to the instrument revision that produced it).
- [pitfall] `.scratch/active-work.md:16` - "**Retraction (2026-10-06 review):** the 14x churn claim (402,984,851 -> 28,191,940) is retracted - it paired the slice-38 **drift** arm with the slice-39 **adversarial** arm. Like for like on the adversarial arm the figure moved ... about 1.18x" - a headline number produced by comparing across two different configurations had to be retracted - policy candidate (same rule as the benchmark methodology finding: one comparison, one configuration, stated on both sides).
- [pitfall] `.scratch/active-work.md:22` - "**Methodological correction (2026-10-01, recorded in 29):** every per-region axis comparison so far (page size, bloom, compaction trigger) ran CACHE-WARM (5 GB data, 128 GB RAM), so it could only measure CPU effects and cannot speak to layout/I-O effects... Until then 'flat' means 'flat when warm', not 'no headroom'" - the experiment's instance was smaller than cache, so the phenomenon under study was absent and a "no headroom" conclusion was drawn from an instrument that could not have seen headroom - policy candidate (state the minimum instance/scale at which the effect under study is even observable, and refuse to conclude below it).
- [pitfall] `docs/prior-art.md:3` and `README.md:40` ("verify citations before external use") - "Verification status: partial... Nine entries are now verified, one author list was **wrong and is corrected**, and two entries were **deleted**"; the deleted "Tesseract" was one "**neither the author nor the reviewing agent could identify**", and `[unverified]` is still carried inline - citations written from memory were wrong in author, venue, and in two cases in the existence of the system - policy candidate (never cite from recall: verify against an authoritative index or mark unverified inline, and delete a name that cannot be corroborated rather than carry it).
- [doc method] `docs/prior-art.md` - "This file exists because an earlier single-table version marked as 'open' several things that are shipped features, and ended with a novelty claim that its own table contradicted" - the doc's conclusion was refuted by its own table, and the fix was to restructure the file around "What is established - and therefore not a contribution" - policy candidate (a novelty/originality claim must be derived from the table of established work rather than asserted beside it; a document that can contradict itself has no check).
- [pitfall] `.scratch/44-first-trustworthy-curve/issues.md` - "Reused verbatim with cold_0b's default `--checkpoint-bytes/--rotate-bytes 16384`, the declared arm aborts `rc=1` six windows into the 200 rps rung"; "The earlier cold runs' exact cadence is not recorded anywhere in the repo; cold_0b's shipped default is what I could recover, and it does not survive on this instance" - the shipped default could not run the shipped engine in the documented regime, and an earlier run's configuration was unrecoverable so its numbers cannot be reproduced - policy candidate (the shipped default must be exercised end to end on the documented instance, and an unrecorded run parameter makes the run un-reproducible, not merely undocumented).
- [doc method] `.scratch/STATUS.md#8 Environment notes` ("Reviewer hygiene") - "do not use the `oracle` agent as a reviewer - it runs with forked context, inherits the supervisor's framing, and twice produced narration instead of a review (once with a fabricated sub-run id). Use a read-only worker-as-verifier that must paste command output and must write `CANNOT-VERIFY` rather than guess" - the reviewer's independence was destroyed by inherited framing and by not being allowed to answer "cannot verify" - already covered by `fresh_reviewer` and `unverified_is_not_pass`, but the concrete failure (a fabricated sub-run id, and the required `CANNOT-VERIFY` escape) is sharper evidence than the policy currently carries.
- [know-how] `.scratch/STATUS.md#8` - "The box is shared: the same 1 M-doc workload has measured 6,137 / 15,060 / 16,264 docs/s on different runs. Deterministic metrics (bytes, counts, block reads) are the primary evidence; timings must state their concurrency" - on a shared machine a timing is not a reproducible quantity, so the deterministic counters had to be promoted to primary evidence - policy candidate (say which of your numbers are reproducible and which are environmental, and score on the former).
- [project rule] `docs/dev-loop.md#Harness` - "**Pre-register a falsification contract.** As specified, almost any measurement can be read as progress, and every candidate refutation is already pre-labelled as not-a-measurement: a canary is 'a conservative lower bound', an untuned Postgres is 'a strawman', the simulator is 'uncalibrated', the worked example is 'illustrative' (`review-02` F18). Therefore, before any engine exists, pre-register: the falsification hypothesis with its threshold..., the primary metric and its reference, the minimum instance size..., the seed count, the confidence interval..." - a system of excuses had made every outcome unfalsifiable, and the rule written to fix it is explicit - policy candidate (a claim must come with the observation that would refute it, fixed before the run; an escape hatch named in advance is not one).
- [project rule] `docs/dev-loop.md#Baselines` - "Every comparison at **equal durability**. An engine that fsyncs less is not faster; it is a different product", plus the two controls the review demanded ("`flashdb-declared` - the missing control... Comparing learned layout against *other engines* conflates three variables") - a win obtained by relaxing the contract shared by both sides is a different product, and the honest comparison needed a control that differs in one variable only - policy candidate.
- [know-how] `docs/dev-loop.md#Harness` - "Brute-forcing the *same* cost model removes optimisation error only, not model error, so it cannot deliver the purpose it was given: it cannot tell whether the learner is good or merely as good as its own cost model. Ground truth would require executing layouts on hardware" - a check that shares the artefact's assumptions can only prove internal consistency - policy candidate (name what a check cannot prove; a verifier built from the same model is not evidence about that model).
- [project rule] `docs/dev-loop.md#Build order` and `#Deferred implementations, frozen interfaces` - "do not build a database to learn what a database should do"; "Deferring an implementation is cheap; deferring a boundary is not. The reserved interfaces in `contracts.md` are frozen at step 0"; "**the mechanism is boring and enormous, the policy is fun and small.** Building the policy first means the project never ships" - three ordering rules, each derived from where the effort and the thesis value actually sit - policy candidate for the first two (freeze boundaries, defer implementations; build the objective and the metric before the artefact that the metric judges).
- [doc method] `docs/dev-loop.md:1`, `docs/prior-art.md:3`, `docs/objective.md:1`, `docs/engine.md:3`, `docs/design.md:1`, `docs/contracts.md:3`, `docs/learning.md:3` - each doc opens with "Budget: N lines / N chars", and the two over budget carry the debt in-file: "Budget: 335 lines / 34,000 chars  <!-- budget debt: see issue 01-design, "Budget debt" -->" - a declared size budget per SSOT file, with the exceedance recorded as a pointer instead of silently ignored - policy candidate (a doc with no size bound becomes the place everything is appended to; and debt is visible rather than discovered).

## Top 5 by value

1. **Validate the measurement instrument before its numbers are used** (flashdb, `.scratch/STATUS.md:68`, `.scratch/active-work.md:9`): four instrument defects invalidated every per-rung number published before a known commit, so the policy needs a rule that an instrument is itself a deliverable, checked before publication, and that a number names the instrument revision that produced it - no current rule says the measurer must be measured first.
2. **A metric change is not a fix** (auto_maintain_bench, `docs/FAIL_PATTERNS.md:187`): "score impact eliminated but behavior persists" is a defect being deleted from the number rather than from the system, and the policy has no rule that separates changing the acceptance criteria from satisfying them.
3. **Pre-register the observation that would refute the claim** (flashdb, `docs/dev-loop.md#Harness`): the project found that every candidate refutation had already been pre-labelled as not-a-measurement, which is the failure mode a general policy must forbid by requiring a falsification threshold fixed before the run.
4. **Citations written from recall are wrong in ways the author cannot detect** (flashdb, `docs/prior-art.md:3`): author lists were wrong, one cited system did not exist, another was a different system entirely, and the surviving rule is verify-or-mark-unverified-or-delete - directly applicable to every policy and design document an agent writes from memory.
5. **A reviewer must be independent and must be allowed to answer `CANNOT-VERIFY`** (flashdb, `.scratch/STATUS.md#8`): the reviewer that inherited the supervisor's framing produced narration and a fabricated sub-run id, so the policy's `fresh_reviewer` needs the two concrete teeth - no inherited framing, and an explicit cannot-verify answer instead of a guess.

Runner-up worth folding in while editing the policy: **a mandatory step belongs in the engine, not in the agent's memory** (auto_maintain_bench, `docs/brainstorm.md` user reply + the auto-backup fix that followed it), and **a comparison is valid only inside one configuration** (same project, `AGENTS.md#Benchmark Methodology`).
