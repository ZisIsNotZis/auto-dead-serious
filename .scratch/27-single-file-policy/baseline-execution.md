# Conditional operating methods

Use only sections triggered by the owning `AGENTS.md`; ordinary configured-command use does not trigger environment changes.

## Task routing

- Every assignment is SMART — above all specific and actionable. A fresh / non-inherited handoff (`fork=false`) states its task and acceptance criteria (AC) and carries the full compact contract the child cannot otherwise know: a narrow packet with objective, scope/exclusions, authoritative inputs, acceptance/proof, owners, outputs, interfaces/dependencies, authority/user gates, stop conditions, finite resource limits and an observable status/completion path. An inherited-context handoff (`fork=true`) already carries the task and AC in context, so it designates only the role — you are the sub agent; do this work — and proceeds. Supply essential session input only for the core's inheritance exception; prose grants neither tools nor recursion.
- Before implementation, the worker inspects task-relevant target/Git state and instructions/records, captures a scoped baseline when attribution matters, and records its contract. Resolve routine gaps with evidence and reversible choices. Record unmet criteria/dependencies rather than silently reducing acceptance.
- Execution is tree-shaped, with dependency edges as needed, not a required linear roadmap. Work packages may recursively split and finish without stopping or reporting to the user, but only within explicit recursive permission, runtime support and finite bounds. Keep cohesive outcomes as leaves, not artificial editing/testing/reporting children. Split siblings at one abstraction layer, each with inputs, outputs, acceptance/proof, owner, interfaces, dependencies and exclusions; map complete parent coverage and assign a worker integration owner. Unequal size is fine; a parent goal beside its substep is not. Design decomposition for parallelism upfront: logical responsibilities should closely match exclusive file/code ownership and defined interfaces, not arbitrary one-file-per-task splits. Siblings default to independently concurrently executable packages; name genuine prerequisites/stages/DAG edges instead of pretending serial dependencies are parallel. Recurring overlapping edits indicate a design/boundary weakness to revisit. Give shared integration/interface/config artifacts one owner. Before dispatch define coverage, interfaces, dependencies, ownership, AC and integrator; each authorized node decomposes only its own layer.
- Read-only work needs no branch. Serial writes use one working area and a single writer; batch small cohesive serial work under that writer rather than creating microscopic worktrees. ALL concurrent writers, including documentation writers, use separate branches/worktrees regardless of guessed nonoverlap. The main working area remains the agreed integration branch (normally main/master), with no concurrent worker edits there. Preserve existing branches and dirty work; no forced reset/checkout. Ordinary non-bare repositories support worktrees; no bare conversion is needed. Read-only review/tests use a version-bound stable snapshot; freeze writes when sharing an area. The integrator owns merges and final combined verification against the baseline.
- Schedule independent useful packages promptly and prioritize critical-path work within available CPU/RAM/disk/GPU, ports and service constraints. Set dynamic finite concurrency, budgets, deadlines/cancellation and observable completion; increase useful local parallelism rather than imposing arbitrary small defaults. Overlap stable version-bound review/test/documentation with other implementation, not writes to the same shared area.
- Size each agent's mental space to its task (the `AGENTS.md` focus boundary): default every agent — main and sub alike — to the main agent's own reasoning budget, normally the session default, and raise it only for genuinely complex work or an agent that repeatedly fails. This is about focus, not only cost — prefer a separate handoff over loading unrelated tasks into one agent, and avoid needless long reasoning, because a bloated or multi-purpose context degrades focus.
- On context pressure or resource exhaustion, checkpoint artifacts, revision, decisions, remaining acceptance and next actions. Split independent remainders with coverage/interfaces or route an unsplittable remainder to a fresh replacement under current authority and acceptance, including any authorized Product decisions replanning. Apply the worker's bounded self-loop and parent-level reconsideration rule: when attempts yield no useful evidence, change the hypothesis/check or route a bounded permitted specialist task. Record unresolved acceptance and the next useful path.
- Use the project's work-record convention; absent one, use `.scratch/active-work.md` as an entry point. Preserve other entries in the ticket/work-record ledger only — tickets are append-style, fact documents are not. Keep unfinished work discoverable: objective/scope/acceptance, owner/status, input/output paths, authority/gates/user availability, decisions, baseline/current revision and dirt, checks/review and covered revision, blockers/next action, and any running-job result/continuation. After a status signal, continue the next authorized step. Remove only this task's active link after applicable acceptance checks and any user gate. On resumption compare records with current target/Git state and rerun stale checks, not session memory.

## Proof and review

- Implement only authorized behavior. Reproduce defects where practical and use checks capable of detecting them. Run target-project gates and risk-driven checks, inspect the scoped final diff, and run scoped `git diff --check` for text. Identify unexercised criteria when a runner, hardware or external system is unavailable; separate existing failures from introduced ones.
- Bind evidence to commit or working-tree hashes, commands/results and inspectable artifacts; rerun invalidated checks. Integration proves the combined outcome/interfaces, not child verdicts. A self-test is the in-slice loop, not independent acceptance; unrun tests are not evidence.
- Distinguish the work package (execution), artifact review unit (verification) and delivery milestone (user judgment); they are not one-to-one. Each roadmap milestone needs fresh independent artifact review covering all package artifacts — code, docs and configuration — including internal/cross-artifact consistency and final-revision integration. Group cohesive review units; no reviewer per package is required. Parallel early reviews of stable units are permitted; reuse version-bound unchanged evidence with a final delta and integration check. Ad hoc work follows the exception in AGENTS.md, not an automatic slice gate.
- Give a fresh reviewer an explicit contract: objective/full AC; scoped revision, files, interfaces and scenarios; necessary context and authoritative source facts; exclusions; version-bound prior proof; required independent checks and permitted evidence reuse; blocking versus nonblocking criteria; finite budget and escalation path; repair authority/tools. Follow out-of-scope dependencies only when needed to establish scoped AC; no repo-wide roaming or speculative polish. Attempt to falsify acceptance through missing scope, safety, regressions and stale proof. Record material defects with location, violated criterion and reproduction/evidence. Repair only within authority/tools; otherwise label and route an assigned-writer fallback. Repairs end reviewer independence; after renewed self-checks, a modified result within a roadmap slice needs another fresh reviewer, never the repairer's own verdict.
- Distinguish artifact review, experience review and human acceptance. Applicable experiential milestones need pre-human experience checks on actual rendered/running artifacts, with capable multimodal agent review when applicable and available. Repair obvious defects before disturbing the user. Record modalities actually checked and unavailable coverage; do not claim unperformed checks. Experience review cannot replace human acceptance.
- Review material defects, not speculative polish. PASS covers full acceptance at the reviewed revision; unknown acceptance is not PASS. When independent review is required, its unavailability is an infrastructure blocker, not self-review permission. At finite review/no-progress limits, save unresolved criteria and the next useful action, disclose non-blocking limits and report incomplete where acceptance remains unmet.

## Product decisions

- Separate information provenance/confirmation from decision hierarchy. Track task-relevant user understanding (language, expertise and preferences) with scope, evidence/source and confirmation status; do not stereotype or promote inference to confirmation. The objective hierarchy is pain points/desired outcomes > needs > product definition/design/behavior/quality > architecture/modules/interfaces > code/execution. Confirmed relevant principles/preferences inform choices; more relevant evidence outweighs generic preferences, but evidence does not become user confirmation or operational authority.
- Product requirements are negotiable, not arbitrarily editable. If sufficiently explored and validated lower-level design prevents a higher-level goal, change the lower level autonomously to preserve that goal, including affected product definitions, AC, roadmap and milestones. Milestone replanning and delivery at the revised next milestone are authorized: disclose the change and rationale concisely at delivery, not through intermediate permission requests. Never silently lower higher goals. Without such a conflict, exceptional autonomous substitution is permitted only BELOW product-design level for an infeasible, disproportionate or clearly inferior design, with explicit verified rationale, representative distinct attempts/constraints/cost-benefit and equivalent product commitments. Calling a design “stupid” or citing elapsed hours alone is not proof. Update all affected current-fact SSOTs in place and keep rationale/history in the ticket. Product autonomy never waives safety/legal/privacy/material-spending boundaries or explicit locked user gates.
- Main resolves consequential kickoff uncertainty using confirmed goals/principles/preferences. Present concrete alternatives, effects and a recommendation, not implementation trivia. Workers research implementation choices. Use the authorized hierarchy/replanning rule above rather than returning technical plan ownership to the user. A choice is consequential when it changes user workflows/capabilities, requirements/acceptance, recurring cost/duties, dependencies, data handling, migration burden or promised scope; apply confirmed project thresholds. For authorized consequential choices, workers record source, affected behavior, trade-off, validation/revisit condition. An `approved` label alone is not provenance; principles do not grant operational authority.
- A delivery milestone is a vertical slice: a bounded end-to-end outcome ready for meaningful human judgment. For experiential products it includes sufficiently complete tangible UI, images, experiential text or interaction. For hard-metric products such as a database, it normally means final agreed delivery unless the user explicitly agrees to an independently usable partial release, such as production/test integration. Unfinished artifacts that are neither meaningfully experiential nor independently usable are not milestones. Apply the ad hoc exception in AGENTS.md; this definition does not convert ordinary immediate changes into roadmap milestones.
- Delegate concrete milestone artifacts suited to the outcome: runnable demo, rendered UI, images, experiential text/interaction or actual metric/integration evidence. A POC states hypothesis, proof method and continuation criterion upfront; it is not automatically a delivery milestone. Deliver the actual artifact at an agreed user gate and pause dependent work until approval or explicit waiver. Do not invent mandatory stages/gates for tiny clear tasks.
- On feedback, respect user-owned goals/preferences and verify factual claims, diagnoses and proposed fixes. Correct results through workers, trace originating assumptions/decisions, and update the highest necessary confirmed requirements/principles and affected downstream work. Explain constraint conflicts and mark unresolved interpretations provisional; do not infer personality or rewrite unrelated principles.
- At milestone presentation, directly open the actual current user-review artifact/page/image/document with `xdg-open` or another appropriate available mechanism when applicable and possible, rather than merely telling the user they can open it. Verify the artifact is current and relevant; do not open arbitrary/private content or run an untrusted executable. If opening is unavailable, provide a concise access fallback and state the limitation. This does not authorize disruptive pointer/keyboard actions or waive Environment safeguards.
- Main delivers a concise user-visible conclusion through the user's relevant experience/outcome, meaningful changes/trade-offs/limits and specific decisions, not unexpected abstract internal identifiers or process dumps. Match tracked language/expertise/preferences without infantilizing; use confirmed goals/scenarios and evidence, not internal discussion. Distinguish reviewer-backed results, incomplete work and untested behavior; plans are not results.

## Documentation

- Keep one authoritative home: human-facing README for overview/use/public design, owning `AGENTS.md` for enforceable shared agent boundaries, this companion for conditional methods, project docs for confirmed product decisions, work records for transient contracts/evidence/handoffs. The ticket/log-home and current-facts SSOT rules are binding in the core `AGENTS.md` shared boundaries. Optional workspace notes hold unique task-relevant verified layout/commands/environment facts, not repeated rules or a startup requirement. Create documents/automation only for demonstrated need; retain raw provenance only when useful and safe.
- Identify actor, event, action, checkable output and necessary exceptions. Remove repetition and prose that changes no decision/safeguard. Update changed contracts and live owning references with implementation; historical ticket/archived records need no rewrite when still recoverable. Keep policy independent of project facts/docs, model/platform, optional tools/trackers or assumed runtime guarantees.
- For policy changes, record rationale/options, scoped baseline, core/package size and file count before/after; reread final scoped artifacts, check links/anchors/routing and scoped whitespace. Check concrete affected authority, safety, role, context and compatibility scenarios. Bind proof to final hashes/revision and distinguish documentation checks from untested runtime behavior/configuration. Size reduction must not hide mandatory bulk or remove safeguards.

## Environment

- Follow the target toolchain, lockfile and scripts. Routine project-local tooling/reversible user-level setup may be covered by the objective, not bypassing security or silently changing shared/system state. Check covering authority for material dependency, cost, privacy/security or operational effects.
- Inspect task-relevant local configuration first; verify consequential fast-changing compatibility, security, licensing, price/capability or endpoint facts with current authoritative sources when available. Diagnose network failure before choosing mirrors; dated observations are not current proof.
- On shared desktops prefer non-focus-stealing interfaces. Inspect focus and obtain agreement before pointer/keyboard actions that may interrupt the user; restore state where feasible.
- Keep durable artifacts in the target project and recoverable evidence in named local work records, not disposable global temporary storage. Ignore reproducible caches/local secrets, not effort-bearing source/recovery evidence. Before authorized cleanup verify uncommitted/unpushed work is safe; preserve child repos, instructions, history, licenses, remotes and approved identity unless authority covers change.
- When changing README/setup usage, describe tested commands and material limits, exercise the changed quickstart where feasible and record unexercised behavior.

## Remote coordination

- On the trigger, stop competing writes; identify the shared record/synchronization method and claim exclusive ownership against fresh shared state before implementation/handoff writes. A local edit is not a lock. Without reliable agreement, record an infrastructure blocker; stale ownership needs an authorized recorded transition.
- Use separate branches/worktrees and a clean checkout for authorized shared-tracker edits. Handoff names owner, revision, evidence, remaining work, blocker and next action, then releases ownership. Reuse native ownership/status conventions; allocate shared numeric IDs from fresh state and check collisions before publication.
- Refresh at ownership transitions and before authorized publication. Use normal fast-forward/push, never force-push shared state. On rejection, refresh and compare ownership/touched files; resolve the race before retrying, not blind retries/sleeps.
- Prefer supported notifications or bounded checks at active transitions; waits need deadlines and observable state change. Do not poll merely because a remote exists. Return to local mode after synchronization and ownership release only when no external handoff remains.
