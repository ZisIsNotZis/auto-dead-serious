# Execution, handoff, and validation

Use when executable work needs checks, or work needs a durable handoff, concurrent ownership, delegation, or a review trail. A self-contained task finished in one session needs no ticket merely because code or multiple files changed.

## Delivery and evidence

- Implement the approved behavior without silently widening contracts. For defects, reproduce where practical and use a check capable of catching the failure. Run applicable project gates and risk-driven checks; inspect the scoped diff and run `git diff --check` for textual changes. If hardware, external systems, or a runner is unavailable, perform feasible checks and name the unexercised behavior.
- Tie a completion claim to the command/result or inspected artifact and the actual commit or working-tree revision. Rerun checks invalidated by later edits. Resolve first-party failures or explicitly report them; a worker verdict or unrun test is not evidence. For consequential subjective output, seek independent review if useful; otherwise state the self-review limit.
- When attempts stop yielding evidence, change the hypothesis or method, narrow reproduction, seek review, or continue independent work. Use specialist help when available and worthwhile; otherwise perform feasible research, experiments, and self-review. Elapsed time, failed attempts, and optional-tool absence are prompts to adapt, not permission or user-contact gates.

## Autonomous progress and waiting

- Record explicit autonomy or user absence, the authorized objective, constraints, and completion criteria in the current work record when work needs continuity. Resume from that authority and current project evidence. Follow confirmed principles and design before inventing a new direction; resolve gaps using the decision policy and verify the result.
- After a progress update, take the next executable step. Before a long operation, identify the result path, deadline or cancellation path, and how processing resumes. Prefer a supported completion notification that actually wakes the agent; otherwise wait for foreground results or use bounded status checks while execution is active. Verify the chosen mechanism in the current environment. Starting a detached job, saving a handoff, or promising future work is not a wake mechanism. Claim background continuation only when it has actually been established.
- If an action requires unavailable user input or authority, record the exact dependency and prepare a recommended direction. Continue safe alternatives and independent work; pause only the dependent action. Honor a pre-agreed acceptance checkpoint for its dependent work, using a concrete demo, artifact, or checkable result rather than an abstract progress label.
- Finish when the authorized objective is delivered and checked, or no meaningful next step remains within current authority and resources. For research, assess remaining avenues against the question: what new evidence could they provide, and would it change the conclusion? Avoid repetitive work without expected information gain. If useful work remains but the environment forces an interruption, state the interruption, actual running work and wake mechanism if any, and the recoverable next step; distinguish that state from completion.

## Recoverable work

- Use a discoverable work record when work spans sessions, concurrent writers, consequential decisions, or a review trail the diff cannot explain. In this workspace, existing local issues live under project-root `.scratch/NN-<feature-slug>/issues/NN-<slug>.md`; reuse one for the same concern. Preserve an existing ticket's status convention rather than inventing a synonym.
- For unfinished work record objective and completion criteria, owner/status, work-item path, branch/revision and relevant dirty files, checks and the revision they cover, granted autonomy and user availability, consequential decisions and provisional assumptions, pending authority or input, blocker, and next executable step (including any running job's result path and wake mechanism). If no current-work entry exists, link active items from project-root `.scratch/active-work.md`; remove completed links. On resume, compare the record with current Git state and rerun stale checks rather than trusting session memory.
- Isolate concurrent writers in separate branches or worktrees; preserve pre-existing changes and integrate only the approved concern. Seek independent review for consequential risk or a declared gate, providing objective, criteria, and scoped revision; record findings and disposition. Low-risk work may use scoped self-review. User review is reserved for a user-owned decision or agreed checkpoint.

## Delegation

- Delegate independently verifiable or specialist work when benefit exceeds handoff cost; duration alone is not a trigger. Assign one owner per task and disjoint ownership to parallel writers. The parent checks evidence, integrates results, and owns acceptance.
- Give a fresh worker objective, scope, authoritative inputs, criteria, constraints, validation, output, and stop condition. Use inherited context only when a compact handoff loses essential meaning. For adversarial critique, provide the artifact and criteria without the author's verdict, then verify findings.
- Define expected progress and cancellation before launch; observe logs, status, and artifacts rather than elapsed time alone. Inspect evidence and try a focused recovery before terminating a stalled worker. Release resources after use. If a worker is unavailable, use safe parent execution or documented self-review and report remaining limitations.
